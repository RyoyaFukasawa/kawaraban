# ops-log — 運用ログ

毎日の日次ダイジェスト routine が、その日の収集状況を `YYYY-MM-DD.md` として
ここに書き出す。週次の改善 routine（[../IMPROVE_PROMPT.md](../IMPROVE_PROMPT.md)）が
このログを集計して `src/feeds.ts` の改善 PR を作る、という自己改善ループの記録場所。

人間がコードを直す必要はない。ログは routine が自動で残す。

## フォーマット（日次 routine が生成）

```markdown
# 運用ログ YYYY-MM-DD

## fetch 結果
| ソース | カテゴリ | 結果 | 取得/新規 | 備考 |
|---|---|---|---|---|
| WSJ Technology | technology | OK | 20 / 20 | |
| WSJ Politics | politics | SKIP | - | HTTP 403 |
| ... | | | | |

- 成功ソース数: X / 全Y
- 候補総数: N件

## カテゴリ別 採用状況
| カテゴリ | 候補 | 採用 | 備考 |
|---|---|---|---|
| technology | 30 | 5 | |
| politics | 45 | 3 | 候補は多いが低品質で3件のみ |
| economy | 29 | 5 | |

## 気づき / 改善候補
- WSJ Politics が継続して 403。サイト改編の可能性、代替フィード要検討。
- politics は件数は出るが速報の重複が多い。中立系の解説ソース追加を検討。
- （新ソース候補があればURLとともにメモ）

## プロジェクト改善考察（収集メモではなく「仕組みをどう良くするか」の所感）
その日の収集結果を踏まえ、**プロジェクトそのものの改善**について考えたことを書く。
ニュース内容の感想ではない。以下の問いを毎日たたき台にする（全部埋めなくてよい、その日に
言えることだけ）。過去のログ（特に `INSIGHTS.md`）を踏まえ、既出の論点は「継続」「悪化」「解消」
のように経過が分かるよう書く。

- **fetch の仕組みは妥当か**: 取得・鮮度フィルタ(36h)・重複排除は意図通り効いているか。
  取りこぼし／取りすぎ／弾きすぎの兆候はないか。
- **本当に最新・先進の情報が取れているか**: 一次情報（公式ブログ・研究所）に対して報道の後追いに
  なっていないか。話題になっている重要トピックで、今のソースでは拾えなかったものはなかったか。
- **ソース構成の穴**: カテゴリ／地域／党派／一次情報の観点で欠けている視点はないか。
  逆に重複・低品質で枠を食っているソースはないか。
- **選定ロジック・枠**: MAX_PER_CATEGORY や選定方針は今の候補の質に合っているか。
  先進性優先のAI枠は機能しているか（埋もれ・薄さはないか）。
- **パイプライン全体**: routine の手順・出力形式・運用に、無駄や壊れやすい点はないか。

> ⚠️ ここは「記録」に徹する。コード（`src/feeds.ts` 等）はこの日次タスクでは変更しない。
> 実際の改善 PR は週次 routine（[../IMPROVE_PROMPT.md](../IMPROVE_PROMPT.md)）が行う。
```

## INSIGHTS.md（累積考察・追記式）
- `ops-log/INSIGHTS.md` は、週次の改善 routine が日次ログの「プロジェクト改善考察」を集約して
  **上書きせず追記していく**累積ファイル。日次ログは1日で流れるが、こちらには
  「経時的に見えてきたこと・繰り返す問題・検証したい仮説・打った手とその後」が残る。
- 日次 routine は INSIGHTS.md を**読んで**考察の土台にしてよいが、**書き込むのは週次 routine だけ**
  （日次が追記すると競合・肥大化するため）。

## 運用ルール
- 1日1ファイル。同日再実行時は追記ではなく上書き更新でよい。
- このログ自体はコミット対象（改善 routine が読むため）。
